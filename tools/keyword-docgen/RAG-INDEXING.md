## What's built (on `main`)

1. **`manifest.json`** (manual root) — every page: `path, keyword, last_updated,
   doc_revision, sha256` (body hash). 933 docs. Regenerated by
   `keyword-docgen version`. Use the `sha256` diff to re-embed only changed pages.
2. **`VERSION`** = `2026.06` (corpus CalVer); **`CHANGELOG.md`**; git tag `docs-2026.06`.
3. **Per-page frontmatter stamps**: `last_updated`, `doc_revision` (incremental —
   only bump on real body change).
4. **`keyword-docgen rag-export`** — emits `rag-chunks.jsonl` (gitignored,
   regenerable). One chunk per page.

### Chunk schema (current)

```json
{
  "id": "02-keywords/.../PosGain.md",          // rel path = stable upsert key
  "keyword": "PosGain",
  "text": "Keyword PosGain (CAN 100; axis; rw; range=[0, 20000]; v4/v5): <summary>\n\n<body>",
  "metadata": {
    "path": "...", "keyword": "PosGain",
    "can_code": 100, "scope": "axis", "units": "user", "range": [0,20000],
    "access": "rw", "data_type": "int32", "availability": {...}, ...,
    "last_updated": "2026-06-02", "doc_revision": "2026.06", "sha256": "…"
  },
  "related": ["PosKi", "VelGain", ...]          // intra-manual links, for graph re-ranking
}
```

- `text` = **synthesized fact header** + body. The header front-loads the facts
  so fact queries ("range of X", "is X available in v5") embed/retrieve well.
- `metadata` = filterable facts + version stamps (filter by `availability`,
  `scope`, `units`; cite by `doc_revision`; re-embed by `sha256`).
- `related` = keywords this page links to.

### Commands

```bash
cd tools/keyword-docgen
MANUAL="../../03 USER MANUALS/00 KEYWORD REFERENCE MANUAL"
# refresh stamps + manifest (incremental):
.venv/bin/python -m keyworddocgen.cli version \
  --content-root "$MANUAL/content" --repo-root ../.. \
  --corpus-version 2026.06 --generated <YYYY-MM-DD> \
  --manifest-out "$MANUAL/manifest.json" --version-file "$MANUAL/VERSION"
# emit chunks:
.venv/bin/python -m keyworddocgen.cli rag-export \
  --content-root "$MANUAL/content" --manifest "$MANUAL/manifest.json" \
  --out "$MANUAL/rag-chunks.jsonl"
```

## Versioning system (how it works — already shipped)

Documentation versioning is implemented and live (baseline `2026.06`). It is
**separate from** the firmware `availability` (v4/v5) facts: `doc_revision` tells
a consumer how current their copy of the *documentation* is; it says nothing
about firmware compatibility. `keyword-docgen version` produces three artifacts:

1. **Per-page frontmatter stamps** — `last_updated` (the page's git last-commit
   date) and `doc_revision` (corpus CalVer), appended *after* the
   generator-owned facts so they never disturb them. Legacy frontmatter-less
   pages are manifest-only (not stamped on disk).
2. **Corpus version** — `VERSION` (`2026.06`), `CHANGELOG.md`, and a git tag
   (`docs-2026.06`) per release.
3. **`manifest.json`** — every page with its `path, keyword, last_updated,
   doc_revision, sha256` (body hash).

**Incremental rule (the important part):** on each run the previous
`manifest.json` is loaded as a baseline. A page whose **body SHA is unchanged**
keeps its prior `last_updated` *and* `doc_revision`; only changed/new pages get
the current version + git date. Two consequences:
- per-page `doc_revision` stays meaningful release-over-release (it marks the
  release a page's prose actually changed in), and
- a stamp/metadata commit never pushes `last_updated` forward (the stamp commit
  becomes the file's git last-commit, but the prose didn't change, so the date
  is held).

**Why the RAG cares:** diff `sha256` between two `manifest.json` pulls to
re-embed *only* changed pages; surface `doc_revision`/`last_updated` in answers
for staleness and citation.

Full reference: the **"Versioning"** section of `README.md`; design + rationale
in the `docs-versioning-scheme` project memory.

## DECISION 1 — embedder / target chunk size (blocks "go")

Measured chunk sizes (est. tokens ≈ words × 1.3, over 933 chunks):

| | tokens |
|---|---|
| median | ~494 |
| p90 | ~958 |
| p99 | ~1751 |
| max | ~6782 |
| **>500 tok** | **452 (48%)** |
| >900 tok | 110 |

- **Large-context embedder (≥8k, e.g. modern OpenAI/Voyage/Cohere):** ship
  document-level largely as-is; only special-case the few >2k-token outliers.
- **Small-context embedder (≤512):** ~48% would be **truncated** — you MUST add
  the **section splitter** below before indexing.

**Action when resuming:** record the embedder + token budget here, then pick the
path.

### Section splitter (TODO, only if small-context)

Plan: for pages over ~400 tokens, split the body by `##` heading into child
chunks; each child inherits the parent `keyword` + full `metadata` + a
`parent_id` back-link, and gets `id = <path>#<section-slug>`. Pages under the
threshold stay whole. (Build as a `--split-sections` flag on `rag-export`, TDD.)

## Diagram plan (TODO)

Corpus has **207 SVG + 34 PNG** image refs; all 241 already have non-empty `alt`.
A text embedding can't see a diagram (200 chunks embed one). Strategy:

1. **Retrieval = text transcript, not raw SVG labels.** SVG `<text>` is just
   disconnected labels ("Kp", "+", "Position") — embeds poorly. Author a 1–3
   sentence **transcript** of signal flow/blocks for the load-bearing diagrams
   (control loops `image60/62…`, timing/WaveDrom). Source it from the existing
   `alt` + the firmware-grounded loop behavior already in the keyword bodies.
2. **Keep transcripts invisible to the doc reader** via an **HTML comment** right
   under the image — renderer-agnostic, truly invisible, no browser config:
   ```markdown
   ![Current control loop](image60.png)
   <!--rag
   Current/torque loop: CurrRef vs measured current → PI (CurrPGain/CurrIGain)
   → voltage command, limited by MaxPWM…
   -->
   ```
   Then teach `rag-export` to detect `<!--rag … -->`, strip the markers, and fold
   the inner text into the chunk `text` (TODO). `alt` stays as the short human caption.
3. **Display/reinjection:** add `images: [paths]` to chunk `metadata` (TODO) so the
   answer step can reinject the actual diagram to the user.
4. **Don't bulk-convert PNGs.** Most SVG bitfield diagrams are already mirrored as
   markdown tables (already retrievable). Only the ~dozen control-loop/timing
   diagrams need transcripts. Optionally re-export those PNGs from their draw.io
   source as SVG (crisp display + real `<text>` in one move).
5. **Optional multimodal:** if your stack has an image embedder, embed the diagram
   too — but transcripts usually beat fuzzy image vectors for schematics. Do
   transcripts first.
